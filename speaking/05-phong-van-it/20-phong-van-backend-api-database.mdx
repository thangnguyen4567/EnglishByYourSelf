# Phỏng vấn Backend, API & cơ sở dữ liệu (Backend, APIs & databases)

<SkillMeta id="noi-20" />

:::info[Mục tiêu]
Phần backend thường chiếm nửa sau của **vòng technical interview**. Tech lead sẽ hỏi cách bạn **thiết kế API**, làm việc với
**cơ sở dữ liệu** (index, transaction, ORM) và xử lý **bảo mật, hiệu năng**. Họ đánh giá độ hiểu sâu (*vì sao*, không chỉ *làm gì*)
và khả năng **so sánh các lựa chọn**. Sau bài này bạn giải thích được các khái niệm backend cốt lõi với ví dụ .NET/EF Core/PostgreSQL
từ hệ thống nhân sự. Ngữ pháp chính: **bị động** (*the request is validated…, the token is signed…*), **câu điều kiện loại 0 và 1**
(*if two users update the same row, …*) và **từ nối** để lập luận (*however, as a result, whereas, so that*).
:::

## 2. Cụm từ & mẫu câu hữu ích

| Mục đích | Mẫu câu | Ví dụ |
|---|---|---|
| Phân biệt 2 khái niệm | *The key difference is that … , whereas …* | The key difference is that authentication checks who you are, whereas authorization checks what you can do. |
| Mô tả luồng xử lý | *When a request comes in, it's first …, then …* | When a request comes in, it's first validated, then passed to the handler. |
| Điều kiện – hệ quả | *If …, the API returns / will …* | If the dates overlap, the API returns a 409 Conflict. |
| Nêu lý do | *We did this so that …* | We added an index so that the monthly report runs in seconds. |
| Kết quả | *As a result, …* / *This meant that …* | As a result, the query time dropped from 8 seconds to 200 milliseconds. |
| Đưa ý phản biện | *However, this only works if …* | However, this only works if the data doesn't change often. |
| Nêu trade-off | *It's a trade-off between … and …* | It's a trade-off between consistency and performance. |
| Chọn giải pháp tùy tình huống | *It depends on … – if …, I'd …; otherwise …* | It depends on the load – if it's read-heavy, I'd add caching; otherwise I'd keep it simple. |
| Câu giờ | *Let me think about that for a moment.* | Let me think about that for a moment – are we talking about reads or writes? |
| Không biết chắc | *I'm not 100% sure, but I'd expect … – I'd verify it by …* | I'm not 100% sure, but I'd expect a lock – I'd verify it by checking the execution plan. |

:::tip[Bị động + điều kiện + từ nối = câu trả lời backend có logic]
- Mô tả hệ thống: *The token **is signed** by the identity server and **validated** on every request.*
- Điều kiện loại 0 (luôn đúng): *If an index **is** missing, the database **scans** the whole table.* Loại 1 (tình huống cụ thể): *If we **cache** this, **we'll need** to invalidate it on update.*
- Từ nối: ***however*** (tuy nhiên), ***whereas*** (trong khi), ***as a result*** (kết quả là), ***so that*** (để mà).

Xem lại: [G19 · Câu bị động](/docs/ngu-phap/g19-cau-bi-dong) · [G20 · Câu điều kiện loại 0, 1, 2](/docs/ngu-phap/g20-cau-dieu-kien-loai-0-1-2) · [G24 · Liên từ & Từ nối](/docs/ngu-phap/g24-lien-tu-tu-noi)
:::

## 4. Câu trả lời mẫu

<SpeakText title="How would you design a REST API for leave requests? (≈ 2 phút)">

I'd start with the resource, which is a leave request. So the main endpoints would be GET on /leave-requests to list them, GET with an ID for one request, POST to create one, and then actions like approve and reject.

For the list, I'd always use pagination, with filters for status, employee and date range, because a big company can have hundreds of thousands of records. The response includes the total count, so the frontend can show page numbers.

When a POST comes in, the payload is validated first – for example, the end date can't be before the start date. Then the business rules are checked in the domain layer. If the dates overlap with an existing request, the API returns 409 Conflict; if the employee doesn't have enough balance, it returns 400 with a clear error message. If everything is fine, it returns 201 Created with the new ID.

Approving is interesting, because it changes two things: the request status and the leave balance. So both updates are saved in one transaction. I'd also use a row version column for optimistic concurrency, so if two managers approve at the same moment, the second one gets a conflict instead of deducting the balance twice.

For security, every endpoint needs an authenticated user, and authorization is done with policies – an employee can only see their own requests, whereas a manager can see their team's. Finally, since POST isn't idempotent, I'd accept an idempotency key from the client so a retry after a timeout doesn't create a duplicate request.

<details>
<summary>Bản dịch</summary>

Tôi sẽ bắt đầu từ tài nguyên, tức là đơn nghỉ phép. Vậy các endpoint chính là GET trên /leave-requests để liệt kê, GET kèm ID để lấy một đơn, POST để tạo đơn, và các hành động như duyệt và từ chối.

Với danh sách, tôi luôn dùng phân trang, có bộ lọc theo trạng thái, nhân viên và khoảng ngày, vì một công ty lớn có thể có hàng trăm nghìn bản ghi. Phản hồi có kèm tổng số bản ghi để frontend hiển thị số trang.

Khi một request POST đến, dữ liệu được kiểm tra trước – ví dụ ngày kết thúc không được trước ngày bắt đầu. Sau đó các quy tắc nghiệp vụ được kiểm tra ở tầng domain. Nếu ngày nghỉ trùng với đơn đã có, API trả về 409 Conflict; nếu nhân viên không đủ số ngày phép, trả về 400 kèm thông báo lỗi rõ ràng. Nếu mọi thứ ổn, trả về 201 Created với ID mới.

Việc duyệt đơn khá thú vị, vì nó thay đổi hai thứ: trạng thái đơn và số ngày phép còn lại. Nên cả hai cập nhật được lưu trong một transaction. Tôi cũng dùng cột row version cho optimistic concurrency, để nếu hai quản lý duyệt cùng lúc, người thứ hai sẽ nhận lỗi xung đột thay vì trừ phép hai lần.

Về bảo mật, mọi endpoint đều yêu cầu người dùng đã xác thực, và phân quyền được làm bằng policy – nhân viên chỉ xem được đơn của mình, trong khi quản lý xem được đơn của cả đội. Cuối cùng, vì POST không idempotent, tôi sẽ nhận một idempotency key từ client để việc gửi lại sau khi timeout không tạo ra đơn trùng.

</details>

</SpeakText>

<SpeakText title="What is the N+1 query problem, and how do you avoid it in EF Core?">

The N+1 problem happens when you load a list with one query, and then run one extra query for each item in that list. For example, we had a report that loaded 500 employees and then, inside a loop, accessed each employee's department. With lazy loading turned on, that meant 501 round trips to the database, and the report took about ten seconds. The fix is to load the related data up front – either with Include, or better, with a Select projection that returns only the columns the report needs. After that change, it was one query and under 300 milliseconds. And for other read-only queries that still return full entities, we use AsNoTracking, so EF Core doesn't waste time tracking changes.

<details>
<summary>Bản dịch</summary>

Lỗi N+1 xảy ra khi bạn tải một danh sách bằng một truy vấn, rồi chạy thêm một truy vấn cho từng phần tử trong danh sách đó. Ví dụ, chúng tôi có một báo cáo tải 500 nhân viên rồi trong vòng lặp lại truy cập phòng ban của từng người. Khi bật lazy loading, điều đó nghĩa là 501 lượt gọi xuống database, và báo cáo mất khoảng mười giây. Cách sửa là tải dữ liệu liên quan ngay từ đầu – dùng Include, hoặc tốt hơn là dùng phép chiếu Select chỉ trả về các cột báo cáo cần. Sau thay đổi đó, chỉ còn một truy vấn và dưới 300 mili giây. Còn với các truy vấn chỉ đọc khác mà vẫn trả về entity đầy đủ, chúng tôi dùng AsNoTracking để EF Core không tốn thời gian theo dõi thay đổi.

</details>

</SpeakText>

<SpeakText title="What's the difference between authentication and authorization?">

Authentication answers the question "Who are you?", whereas authorization answers "What are you allowed to do?". In our system, a user logs in through the identity server and gets a JWT, which is signed and validated on every request – that's authentication. Authorization happens after that. For example, every logged-in user can open the payroll module, but only HR staff can see other people's salaries, and a manager can only approve leave for their own team. If authentication fails, we return 401; if the user is known but not allowed, we return 403.

<details>
<summary>Bản dịch</summary>

Xác thực trả lời câu hỏi "Bạn là ai?", trong khi phân quyền trả lời "Bạn được phép làm gì?". Trong hệ thống của chúng tôi, người dùng đăng nhập qua identity server và nhận một JWT, được ký và kiểm tra ở mọi request – đó là xác thực. Phân quyền diễn ra sau đó. Ví dụ, mọi người dùng đã đăng nhập đều mở được module tính lương, nhưng chỉ nhân sự phòng HR mới xem được lương của người khác, và một quản lý chỉ duyệt được đơn nghỉ của đội mình. Nếu xác thực thất bại, chúng tôi trả về 401; nếu biết người dùng là ai nhưng họ không có quyền, chúng tôi trả về 403.

</details>

</SpeakText>

:::note[Phân tích bài mẫu]
- **Bài thiết kế API:** đi theo luồng **tài nguyên → danh sách & phân trang → tạo mới & validation → nghiệp vụ phức tạp (transaction, concurrency) → bảo mật → idempotency**. Mỗi ý đều có mã HTTP hoặc ví dụ cụ thể.
- **Bài N+1:** định nghĩa một câu → ví dụ thật có số liệu (*501 round trips, ten seconds*) → cách sửa → kết quả sau khi sửa.
- **Ngữ pháp:** bị động (*the payload is validated, both updates are saved*), điều kiện (*If the dates overlap, the API returns…*), từ nối (*whereas, so, finally, since*).
- **Mẹo:** câu so sánh 2 khái niệm luôn mở bằng *X answers…, whereas Y answers…* rồi đưa ví dụ – ngắn, rõ, dễ nhớ.
:::

## 5. Bài tập tự luyện

1. **Ngày 1:** Học 3 bảng từ vựng (bấm 🔊), đặc biệt *idempotent, authorization, execution plan, deadlock*.
2. **Ngày 1:** Chọn **một tài nguyên trong dự án của bạn** (ví dụ: hợp đồng, bảng chấm công, phiếu đánh giá), mở **🧭 Dàn ý** dưới danh sách câu hỏi chính và trình bày thiết kế API theo 3 cấp: **Cấp 1** (từ khóa, ~30 giây) → **Cấp 2** (câu khung, ~1 phút) → **Cấp 3** (mở rộng với số liệu & bài học, ~2 phút). Ghi âm mỗi cấp, thay chi tiết đơn nghỉ phép bằng tài nguyên **của bạn**; chỉ so với bài mẫu **sau khi** đã tự nói.
3. **Ngày 2:** Shadowing bài N+1 và authentication/authorization, sau đó tự nói lại với ví dụ từ dự án của bạn, mỗi câu 60–90 giây.
4. **Ngày 2:** Trả lời 10 câu hỏi chính. Với mỗi câu, dùng ít nhất **một câu điều kiện** và **một từ nối** (*however, whereas, as a result*).
5. **Nâng cao:** Nhờ bạn hỏi 3 câu follow-up. Luyện trả lời *"It depends on…"* rồi nêu rõ **hai tình huống** và lựa chọn cho mỗi tình huống.
